| 缺口 | DevLoop 那一层补的是什么 | 出处 |
|---|---|---|
| **① 提交前必须确认 HEAD 是隔离分支** | ⛔ 实测过：工人在 worktree 里 `git symbolic-ref HEAD refs/heads/master`，产出被提交到 **master**，而工具还印「仅落在隔离分支，未触碰主线」——**那句话当时是假的** | `worktree.py:102` 注释 · BACKLOG G-54 |
| **② 基点解析** | 干净工作区下 `snapshot_base` 返回字面量 `"HEAD"` ⇒ 必须走 `resolve_base` | `cli.py:761` 注释 |
| **③ 磁盘余量** | 盖房子前先量院子 | `worktree.py:407` |
| **④ 清理失败要喊** | ⛔ 08-22 前静默 ⇒ 2,983 个泄漏 ≈26 GB ⇒ **C 盘被撑爆** | `worktree.py:181` |
| **⑤ 命名/时间戳** | 并发安全 | `naming.py` |

## B.3 ⇒ 结论

⛔ **不是「worktree 的封装」。**
⭐ 五条里 ①②④ 都有**真实事故**做出处 —— ⚠️ 而它们**都不是 git 能提供的**，
是「**用 worktree 做隔离时，工人可能怎么骗你**」的应对。

⇒ ⭐ **latch 需要的不只是一份约定文档**，⛔ 至少 ①（HEAD 断言）和 ④（清理要喊）必须是代码。

# 任务 C · ⭐⭐ 实测：Task 工具的隔离够不够

## C.0 ⛔ 实验设计的一处错误（⭐ 而它是本次最有价值的结果）

**我做的**：在 `%TEMP%/taskc` 建了一个临时 git 仓当靶场，然后派两个
`isolation: worktree` 的 sub-agent。

**⛔ 实际发生的**：探针**根本不在那个靶场里**。它们被放进了：

```
C:/pg/_infra/devloop/.claude/worktrees/agent-a0c2...  [worktree-agent-...] locked
C:/pg/_infra/devloop/.claude/worktrees/agent-a2cb...  [worktree-agent-...] locked
```

⇒ ⭐⭐⭐ **`isolation: worktree` 的作用域不由调用方指定 —— 它按会话所在的仓建。**
⇒ **主控无法把 sub-agent 隔离到一个任意目录。**

> ## ⭐ Task 工具提供的是**隔离**，⛔ 不是**可控的隔离**。

⚠️ 这条只有实测拿得到，⛔ 读文档读不出来。
⚠️ 它同时意味着我**违反了「实测在临时目录做」这条铁律** —— 如实记录。

## C.1 逐条实测结果

| 问题 | 实测答案 | 证据 |
|---|---|---|
| **隔离 · 读对方工作区** | ⛔ **能读** | 探针 A 返回原文：**「Confirmed cross-worktree read」** |
| **隔离 · 读对方的对话记录** | ⛔⛔ **能读** | 探针 B 返回原文：**「I can read A's full transcript and tool outputs」** |
| **隔离 · 写主仓** | ⛔⛔⛔ **能写** | 实验后 `C:/pg/_infra/devloop/shared.txt` 内容为 `A-touched-main` + `B-touched-main` —— **两个探针都从「隔离」工位里写进了主仓** |
| **配额 · 限总花费 / 调用次数 / 墙钟** | ⛔ **做不到** | Agent 工具的返回只有 `agentId` + `output_file` 路径，⛔ **无花费字段、无调用次数字段、无墙钟字段** |
| **台账 · 结果以什么形式留下** | ⚠️ 一份 JSONL transcript（路径在返回里）| ⛔ 但**没有结构化的成败字段**；⚠️ 而且探针 B 证明**别的 agent 读得到它** |
| **失败 · 主控怎么知道** | ⛔ **只有文字** | 两个探针都是被用户掐掉的，主控收到的 `status` 是 `killed` + 一段**自然语言 result**。⛔ **没有退出码** |

## C.2 ⚠️ 本次实测的射程

⛔ **两个探针都被用户中途掐掉**（`status: killed`），⇒ **未跑完全部探测项**。
⭐ 但上表每一条都基于**已返回的真实输出**，⛔ 无推测项。
⚠️ 未取得的：「写对方工作区」是否成功、「写共用 `.git/hooks`」是否成功 —— **判断不了**。

## C.3 ⇒ 直接回答你要的两问

**Q · 若 latch 要在 A 仓里判定 B 仓的产物，Task 的 worktree 隔离够不够？**

> ## ⛔ **不够，而且差得远。**

三条独立理由，每条都足以否定：

1. ⛔ **作用域不可控**（C.0）—— 工位建在**会话所在的仓**，latch 无法指定「隔离到 B 仓」
2. ⛔ **写主仓无阻拦**（C.1）—— 实测两个探针都写进去了
3. ⛔ **失败只有文字**（C.1）—— 而 latch 的 M1 立身之本是「pass/fail 由**退出码**决定，模型只出意见」
   ⇒ **Task 工具连退出码都不给主控。**
   ⚠️ **第 3 条的射程后被 latch 侧收窄** —— ⭐ 见 **§C.4 补记**（结论 1、2 不受影响）。

**Q · DevLoop 的 `Worktree` 那一层，是不是正好在补这个？**

⭐ **部分是，但对不齐：**

| DevLoop 补的（任务 B）| 对应 Task 的哪个洞 |
|---|---|
| ① HEAD 断言（防工人把产出提交到主线）| ⭐ **正好补 C.1 的「写主仓」** |
| ④ 清理失败要喊 | ⚠️ Task 的工位是 `locked` 的，⛔ 泄漏形态不同 |
| ②③⑤ 基点/磁盘/命名 | ⛔ **与 Task 的洞无关** |

⇒ ⭐ **五条里只有 ① 直接对应。**⛔ 其余是「用 worktree 做隔离」这件事本身的坑，
与用不用 Task 工具无关。

# C.4 · ⭐ 补记：架构 B 下的 M1（latch 侧澄清，2026-08-22）

> ⛔ **本节不改动 C.1–C.3 的任何结论**，只收窄 C.3 第 3 条的射程。

## C.4.1 判定者挪一格，M1 就活了

我在 C.3 写的第 3 条隐含了一个错误前提：**判定者是主控**。

| | 链条 |
|---|---|
| ⛔ **错（我原来的隐含前提）** | agent 返回退出码 → **主控**判定 |
| ⭐ **对** | agent 产出 **artifact** → **shell 闸判 artifact** → **闸**给退出码 |

⇒ **判定者是 shell，不是 agent，也不是主控。**

⇒ ⭐⭐ **「agent 没有退出码」不是缺陷，是正确的。**
⛔ agent 自报退出码**反而违反 T1（判定者不得是被判定者）** ——
那等于让被考的人自己填分数栏。

## C.4.2 ⭐ DevLoop 已经是这么做的（可核查）

⚠️ 这不是设想，`devloop/gates.py:612` 就是这条链：

```python
def run_on_commit(paths, commit="HEAD", **kw) -> GateResult:
    """把指定提交检出到一次性 worktree 再验。
    ...
    **工作目录会撒谎，提交不会。**"""
```

| 链条一环 | DevLoop 里的对应物 |
|---|---|
| artifact | ⭐ **一个 commit**（⛔ 不是工作区 —— 工人可能留未暂存文件）|
| 判定者 | `.devloop/gates.sh`，在**一次性 detached worktree** 里跑 |
| 退出码 | `gate_code`：**0** 全过 · **1** 有未过 · ⭐ **2 闸自身故障** |

⇒ ⭐ **C.1 那张表里「失败只有文字」量的是 Task 工具的返回**，
⛔ 而在这条链里，主控**根本不需要**读 agent 的返回来判定 —— 它读闸的退出码。

## C.4.3 ⚠️ 但澄清没有解除另外两条

| C.3 的理由 | C.4 之后 |
|---|---|
| 1 · 作用域不可控 | ⛔ **原样成立**（判定者挪格不改变工位建在哪）|
| 2 · 写主仓无阻拦 | ⛔ **原样成立**（判定者挪格不阻止越界写）|
| 3 · 失败只有文字 | ⭐ **撤销** —— 判定不经过 agent 的返回值 |

⇒ ⭐ **Q1 的答案「不够」不变**，⛔ 但支撑它的从三条变成**两条**，
且两条都是**隔离**问题，⛔ 不是**判定**问题。
⇒ ⭐⭐ **判定层 latch 已经有答案了（shell 闸）；没答案的是强制层。**

## C.4.4 ⛔ 澄清带进来一条新要求

判定者挪到 shell 之后，出现一个 agent-退出码方案里不存在的失效模式：

> ⛔ **agent 根本没产出 artifact**（崩了 / 被掐 / 空转），
> 而闸拿到的是「没有可验之物」。

⇒ ⭐ **artifact 缺失必须判 FAIL 或 VOID，⛔ 绝不许判 PASS。**

⚠️ DevLoop 在这一条上栽过：`dossier.py:107` 的注释记着二次订正 ——
第一版把「没点名的」分成两拨，于是**验过而且通过**的被印成「都是 SKIP/VOID——没验」。
⭐ 收口是分成**四拨**（fail / unknown / pass / vacuous），
且 `dossier.py:147` 逐字写着「**SKIP/VOID＝没验，⛔ 不是「验过没事」**」。

**实测数字（本次 prune 前后）：**

| | prune 前 | prune 后 |
|---|---|---|

### 当前清理路径有没有 `prune`？

⛔ **没有。**

| 位置 | 做了什么 | 有 `prune` 吗 |
|---|---|---|
| `worktree.py::remove` :181 | `git worktree remove --force` + `git branch -D`，失败**喊出来 + 记数**（08-22 修）| ⛔ **无** |
| `gates.py::run_on_commit` 的 `finally` | `git worktree remove --force`，失败喊出来（08-22 修）| ⛔ **无** |
| `prune.py`（模块名叫 prune）| ⭐ **列**可清理的分支与 worktree | ⛔ **不执行 `git worktree prune`** |

### 该不该加？（⛔ 只判断，不改代码）

⭐ **该加**，三条理由：

1. ⭐ **它就是 T5 的形状**：`remove` 失败会喊，⛔ 但「remove 成功了、登记残留」**不产生任何输出** ⇒ 速率 > 0 ⇒ 必然累积。**实证 3,016 条。**
2. ⭐ **代价可测**：本次 3,016 条 `prune` 用时 **6.8 秒**。
3. ⚠️ **它有真实后果**：`git worktree list` 从 26 KB 涨到 **362 KB**
   ⇒ 任何读这个输出的代码/人都要处理 14 倍的噪音。⭐ 本次核验中我自己就被它刷屏两次。

⛔ **但我不下「加在哪」的结论** —— 那是提方案，超出本次核验范围。
