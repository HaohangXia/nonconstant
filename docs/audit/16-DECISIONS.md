## §1 关于基座

### D-01 · 建在 spec-kit 上,不自建 CLI

| | |
|---|---|
| **决定** | nonconstant 建在 `github/spec-kit` v1.0.0 之上 |
| ⛔ **拒绝** | 自建工作流引擎与 CLI |
| **理由** | 实测:spec-kit 有 1,788 行工作流引擎。`workflows/steps/shell/__init__.py:70` —— `returncode != 0` ⇒ `StepStatus.FAILED` ⇒ `RunStatus.FAILED` ⇒ 流水线停止。`continue_on_error` 需显式开启。**阻断能力已存在,不必重写。** |
| **来源** | nonconstant 侧实测 v0.16.4 → v1.0.0 复核 |
| ⚠️ **修正史** | 早期判断"spec-kit 无 runtime,结构上无法阻断"—— ⛔ **错**。见 `01-PLAN.md` §8 #4/#5/#6 |

### D-02 · 一行不改上游

| | |
|---|---|
| **决定** | `vendor/spec-kit/` 只读。nonconstant 全部为新增文件 |
| ⛔ **拒绝** | fork 后修改;改 `HookExecutor` 让 hook 真阻断 |
| **理由** | Chesterton's Fence:**KEEP 是零举证的默认态**,DELETE 需举证,MODIFY 举证最重。且上游 1795+ commits、迭代频繁,改动面正是合并冲突高发区 |
| **来源** | 用户 2026-08-21:「别人已经写好的东西我就先拿着,删除还要花时间精力,还得考虑依赖」 |

### D-03 · 不删 extensions / presets

| | |
|---|---|
| **决定** | 保留全部 spec-kit 代码,不做任何删减 |
| ⛔ **拒绝** | 删 `extensions/` + `presets/` 减重约 16,000 行 |
| **理由** | ① KEEP 零举证,而删除需举证 —— **我们制造了一个本不需要论证的问题并为它消耗了三轮**;② 实测依赖方向是 `workflows → extensions`(相对导入 `from ...extensions import normalize_priority`),删除会打断引擎;③ nonconstant 的价值是**新增契约治理层**,不是精简上游 |
| **来源** | nonconstant 侧实测 + `01-PLAN.md` §8 #9 |
| ⭐ **顺带事实** | `workflows → extensions` 的全部依赖面 = 单个函数 `normalize_priority`(`extensions/__init__.py:185-204`),闭包仅含常量 `DEFAULT_HOOK_PRIORITY = 10`。**8,020 行里被依赖的是这 20 行** |

## §4 关于方法论本身

### D-15 · T5 · 静默失败必然累积到灾难规模

| | |
|---|---|
| **定理** | 任何可能失败的操作,若其失败**不改变任何可观测输出**,则该失败**必然**被累积到灾难规模 |
| **推导** | 失败无输出 → 无人知晓 → 无人修 → 累积;累积速率 > 0 ⇒ 必然到达灾难阈值。⭐ **与失败率高低无关** |
| ⭐ **实证** | 86 GB 撑爆 C 盘:2,983 个泄漏工位 ≈26 GB + pytest 临时目录 60 GB。根因 = `capture_output=True` 且不查返回码,清理失败被完全吞掉 |
| ⭐ **可机器检查** | 扫 `capture_output=True` 不查返回码 / `except: pass` / `\|\| true` / `2>/dev/null` |
| ⚠️ **扫描单位** | ⛔ **必须用函数作用域,不用行数窗口** —— 实测行数窗口(8 行)误报率 10%,函数作用域降到 0 |

### D-16 · 判据不能是常量

| | |
|---|---|
| **判别式** | ⭐ **若一条判据对任何输入都返回相同结果,它不是判据,是常量** |
| **元判据** | 判据加入或修改时,必须证明 ① 在预算内可执行 ② **能产出非常量结果**(演示至少一次过 + 一次失败) |
| ⭐ **实证** | DevLoop 某判据 **08-17 退化成必然红**,08-20 才被观察到 —— 而 08-17→08-20 之间**闸跑了 0 次** |
| ⚠️ **补一维** | ⛔ 任何"连续 N 次同值"检测都抓不到"**根本没跑**" ⇒ 需要「判据最后一次执行时间超阈值 ⇒ 报警」 |

### D-17 · 红检必须配绿检

| | |
|---|---|
| **决定** | 每条判据必须同时演示"该红时红"与"该绿时绿" |
| **理由** | ⛔ 只做红检,分不出「判据正常」与「判据卡在红」。实测:那条判据一直是红的,红检照样通过 —— **通过的原因是错的** |

### D-18 · 落盘纪律

| | |
|---|---|
| **决定** | 任何跨 session 的结论,**必须先落盘再讨论**。顺序:产出 → 写入 `docs/audit/` + commit → 才进入讨论 |
| **理由** | ⛔ 反过来会让状态只活在对话上下文,换 session 即丢失 ⇒ **必然漂移** |
| ⭐ **实证** | 04/06/08 三份核验报告一度**从未提交**,而它们是 §8 #11/#12/#14 的唯一证据来源 —— **证据未入库,结论已写进真源** |

### D-19 · 契约变更必须走独立入口

| | |
|---|---|
| **决定** | 对已冻结契约的变更须:独立入口 + 列影响面 + 要求下游重验 + 记录"为什么当时是错的" |
| ⭐ **实证** | `01-PLAN.md` §8 #13 —— 一次变更混在技术回复的摘要表里,未列影响面,未要求重验,两次问询用户未获答复却已标"采纳",并被判为 CONVERGED |

### D-20 · 收敛判据

| | |
|---|---|
| **决定** | ⭐ **结束条件 = 新一轮的发现不再改变"下一步"** |
| ⛔ **拒绝** | "所有问题答完才算结束" |
