## 第一步:干净推导(必做,不可跳过)

**不要先读 `01-PLAN.md` 的 §1。**先自己从下面三条公理推导,推完再去对照。

- 公理 1:模型在两次运行之间遗忘一切
- 公理 2:生成成本崩塌,验证成本不变
- 公理 3:错误成本三重不对称(生成≈0 / 发现=高 / 修复已被依赖的错误=指数增长)

推出你认为成立的定理(至少 3 条),然后与 `01-PLAN.md` §1 的 T1–T4 逐条比对:

| 比对结果 | 动作 |
|---|---|
| 推出了文档没有的 | 候选提案 `ADD` |
| 文档有但你推不出来 | 候选提案 `DELETE` / `MODIFY`,说明推不出的原因 |
| 一致 | 记录一致,**不产生提案** |

**这是防文档臃肿的主力机制。推不出来的东西不配留着。**

## Chesterton's Fence(涉及 spec-kit 代码时必答)

> spec-kit 由 GitHub 及大量贡献者写成,1795+ commits。
> **默认假设:每处设计都有理由,只是我们还没看见。**

| 处置 | 举证责任 |
|---|---|
| KEEP | 无(默认态) |
| DELETE | 证明无其他组件依赖 + 说明其职责在 latch 中由谁承担 |
| **MODIFY** | **先重建原设计意图**,再论证我们场景的实质差异 |

四问:
1. 它防的是什么?
2. 证据在哪?(commit / issue / 注释 / 相邻代码形状 —— 至少一处可核查)
3. 那个问题在 latch 场景下还存在吗?
4. 我们错了会怎样?失效模式?可逆吗?何时发现?

**铁律:答不上来 → 一律 KEEP,写进未决问题。**
**"我不知道它为什么这么写"是 KEEP 的理由,不是 DELETE 的理由。**

**不对称:DELETE 比 MODIFY 安全。**整块删掉行为可预期;改内部逻辑则"以我们不完全理解的方式存在"。两者都可行时优先 DELETE。

## 第三步:打 Benefit 分(0 ~ +5)

| 分 | 锚点 |
|---|---|
| +5 | 修复一个会让核心主张失效的缺陷 |
| +4 | 显著提升硬约束覆盖,或消除一个已记录副作用 |
| +3 | 明确改善,不触及核心 |
| +2 | 边际改善 |
| +1 | 措辞/结构 |
| 0 | 无实质改善 |

**你不打 Cost 分。**那是 Challenger 的事。
